Sharding en PostgreSQL

Guía y casos de uso

Dividir una base grande para escalar sin perder coherencia.

El sharding divide los datos de una tabla grande entre varios servidores para escalar horizontalmente cuando un único nodo ya no alcanza en almacenamiento, escrituras o CPU.

Sharding Reparte filas entre varios servidores
Particionamiento Divide una tabla dentro de un mismo servidor
Replicación Copia todo el dataset a otros nodos

Qué es el sharding

El sharding divide los datos de una tabla grande entre varias bases de datos independientes (shards), de modo que cada una guarda solo una parte de las filas. Sirve para escalar horizontalmente cuando un único servidor ya no alcanza en almacenamiento, escrituras o CPU.

Cada shard es una base de datos completa, normalmente en su propio servidor, con el mismo schema que los demás. La tabla pedidos existe en cada base con las mismas columnas, pero cada una contiene solo los pedidos de un subconjunto de usuarios.

Concepto Qué hace Donde vive Para qué sirve
Sharding Divide filas entre varias bases Varios servidores Escalar escrituras y volumen de datos
Particionamiento Divide una tabla en partes Un solo servidor Mantenimiento y consultas más rápidas
Replicación Copia todos los datos Varios servidores Respaldo y lecturas distribuidas

Cómo funciona

Una función determinista decide en qué shard cae cada fila a partir de la shard key, una columna como user_id o tenant_id. El router calcula la ubicación, y como usa la misma función al escribir y al leer, siempre llega al mismo lugar. 

SHARDS = {
    0: "postgres://db1.miempresa.com/app",
    1: "postgres://db2.miempresa.com/app",
    2: "postgres://db3.miempresa.com/app",
}

def shard_para(user_id):
    return SHARDS[hash_estable(user_id) % 3]

La shard key y estrategias de distribución

Estrategia Cómo reparte Ventaja Riesgo
Hash hash(user_id) % N Reparto uniforme Consultas por rango son costosas
Rango Usuarios de 1 a 1M en shard A Fácil de entender Picos de carga por rangos consecutivos
Directorio Tabla de mapeo por clave Flexible y mobile Consulta extra y más mantenimiento

Qué exige este diseño

  • La consulta debe incluir la shard key para que el router pueda enviar la solicitud a un solo shard.
  • Tablas relacionadas deben compartir la misma clave para que los joins sean locales.
  • Las migraciones de schema se aplican en todos los shards.
  • Tablas pequeñas o maestras suelen replicarse en cada shard.

Opciones para implementarlo en PostgreSQL

Casos de uso

Caso Shard key típica Por qué encaja
SaaS multi-tenant tenant_id Se aislan clientes grandes y todas las consultas de un cliente van al mismo shard.
Aplicaciones con millones de usuarios user_id Las lecturas y escrituras de cada usuario quedan juntas.
Alto volumen de escrituras user_id o device_id Cada shard absorbe una parte de la carga.

Desafíos y cuándo no conviene

  • Consultas entre shards: JOINs y agregaciones sobre varios nodos son más lentos.
  • Transacciones distribuidas: consistencia entre varios servidores es compleja.
  • Rebalanceo: agregar o quitar shards implica mover datos.
  • Complejidad operativa: backups, monitoreo y migraciones se multiplican.
Regla práctica: antes de sharding, probar índices, particionamiento, replicas y caché. Si después de esto sigue habiendo cuello de botella por volumen o por escrituras, sharding es razonable.

Sharding con CQRS

CQRS combina bien con sharding: cada lado, escritura y lectura, puede shardear por su propia clave. El cluster de escritura guarda el estado real, y el cluster de lectura proyecta datos en uno o varios modelos optimizados para consultas frecuentes.

En costo-beneficio, si el objetivo es solo sacar lecturas del primario, replicas de lectura suelen ser suficientes. Si la consulta requiere otra forma de modelado o otra shard key, CQRS completo gana.
