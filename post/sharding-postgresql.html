Sharding en PostgreSQL: guía y casos de uso

Qué es el sharding

El sharding divide los datos de una tabla grande entre varias bases de datos independientes (shards), de modo que cada una guarda solo una parte de las filas. Sirve para escalar horizontalmente cuando un único servidor ya no alcanza en almacenamiento, escrituras o CPU.

Cada shard es una base de datos completa, normalmente en su propio servidor, con el mismo schema que los demás. Por ejemplo, la tabla pedidos existe en las tres bases con las mismas columnas e índices, pero cada una contiene solo los pedidos de un tercio de los usuarios.

PostgreSQL no trae sharding automático. Incluye particionamiento declarativo y Foreign Data Wrappers, pero repartir los datos entre servidores requiere una extensión (Citus), un proxy o lógica en la aplicación.

Sharding, particionamiento y replicación

Los tres conceptos se confunden seguido, pero resuelven problemas distintos: el sharding reparte los datos entre servidores, el particionamiento los reparte dentro de un servidor y la replicación los copia completos.

Concepto Qué hace Dónde vive Para qué sirve Soporte en PostgreSQL
Sharding Divide las filas entre varias bases Varios servidores Escalar escrituras y volumen de datos Requiere Citus, proxy o lógica en la app
Particionamiento Divide una tabla en partes Un solo servidor Mantenimiento y consultas más rápidas Nativo (PARTITION BY RANGE, LIST, HASH)
Replicación Copia todos los datos a otros servidores Varios servidores Respaldo y repartir lecturas Nativa (streaming y lógica)

En la práctica se combinan: cada shard puede tener sus propias réplicas, y las tablas dentro de un shard pueden estar particionadas.

Cómo funciona

Una función determinista decide en qué shard cae cada fila a partir de la shard key, una columna como user_id o tenant_id. El router no busca el dato: lo calcula, y como usa la misma función al escribir y al leer, siempre llega al mismo lugar.

Para user_id = 7 el router calcula 7 % 3 = 1 y envía la consulta solo al Shard 2, mientras los otros dos no participan. El ejemplo usa el valor directo por simplicidad: en la práctica se aplica antes una función hash estable.

La shard key y las estrategias de distribución

Estratégia Cómo reparte Ventaja Riesgo
Hash hash(user_id) % N Reparto uniforme Las consultas por rango son costosas
Rango Usuarios 1 a 1M en el shard A Simple de entender Puntos calientes si las altas son consecutivas
Directorio Una tabla que mapea cada clave a su shard Flexible: se puede mover una clave puntual Una consulta extra y un punto más que mantener

El router de shards

El router necesita dos cosas: la función de distribución y una tabla que mapea el resultado a una conexión real. Dónde vive depende de la opción elegida. 

SHARDS = {
    0: "postgres://db1.miempresa.com/app",
    1: "postgres://db2.miempresa.com/app",
    2: "postgres://db3.miempresa.com/app",
}

def shard_para(user_id):
    return SHARDS[hash_estable(user_id) % 3]

conn = conectar(shard_para(7))
conn.execute("SELECT * FROM pedidos WHERE user_id = 7")

Claves que no son números: UUID y texto

Se usa un hash del valor, no el valor mismo: UUID, bytes, hash, entero, módulo. La función hash tiene que ser estable entre ejecuciones (md5, xxhash, murmur3). El hash() incorporado de Python no sirve, porque devuelve valores distintos en cada proceso. 

import hashlib, uuid

def shard_para(user_id: uuid.UUID, n_shards=3):
    h = hashlib.md5(user_id.bytes).digest()
    return int.from_bytes(h[:8], "big") % n_shards

Un UUID v4 es una buena shard key: reparte parejo y se genera sin coordinación entre shards, algo que un BIGSERIAL no permite. Con UUID v7, que empieza con una marca de tiempo, conviene siempre el sharding por hash, porque por rango todas las escrituras nuevas caerían en el último shard.

Qué exige este diseño

  • La consulta tiene que incluir la shard key. Sin ella, el router debe preguntar a todos los shards y juntar los resultados.
  • Las tablas relacionadas deben llevar la misma clave para quedar en el mismo shard y hacer joins locales.
  • Las migraciones de schema se aplican en todos los shards.
  • Las tablas chicas y comunes suelen replicarse completas en cada uno.

Opciones para implementarlo en PostgreSQL

PostgreSQL no trae un router de shards, así que alguien tiene que cumplir ese rol: o lo programás vos, o lo trae una herramienta. La diferencia entre las opciones es cuánto código del router escribís y mantenés.

Opción ¿Escribís el router? Dónde vive el router Cuándo conviene
Sharding en la aplicación Sí Un módulo dentro de tu app Pocos shards y control total sobre el ruteo
Proxy externo No, se configura Un servicio entre la app y las bases Mantener el código de la app casi sin cambios
Citus No El nodo coordinador Multi-tenant y SQL casi completo
Base distribuida compatible No Integrado en cada nodo Reparto automático desde el origen

Sharding en la aplicación

Una función como shard_para(user_id) y un diccionario de conexiones. Da control total, pero el ruteo, las migraciones en todos los shards, el rebalanceo y las consultas entre shards quedan en tu código.

Proxy externo

La app se conecta al proxy creyendo que es una sola base, y este decide a qué shard enviar cada consulta. Se configura la shard key, la cantidad de shards y los servidores. Algunos proyectos son jóvenes y no cubren todo el SQL, por lo que conviene evaluarlos antes de usarlos en producción.

Citus

Es una extensión de PostgreSQL que lo convierte en una base distribuida: un nodo coordinador y varios workers. La app se conecta al coordinador con SQL normal. 

CREATE EXTENSION citus;

SELECT create_distributed_table('pedidos', 'user_id');

Citus aplica la función hash propia del tipo de dato (uuid, int, text) y obtiene un entero de 32 bits. Ese espacio se divide en rangos fijos, cada uno propiedad de un shard, y la metadata vive en el coordinador. Por defecto crea 32 shards lógicos repartidos entre los workers, lo que facilita el rebalanceo.

Casos de uso

El sharding se justifica cuando un solo servidor ya no puede con el volumen de datos o con la carga de escritura, y cuando existe una clave natural por la que casi todas las consultas filtran.

Caso de uso Shard key típica Por qué encaja
SaaS multi-tenant tenant_id Todas las consultas de un cliente van a un solo shard y se puede aislar a los clientes más grandes.
Aplicaciones con millones de usuarios user_id Las lecturas y escrituras de un usuario quedan juntas y la carga se reparte.
Alto volumen de escrituras user_id o device_id Cada shard absorbe una parte de las escrituras.

Se ve mejor con un caso concreto. En una tienda en línea con pedidos shardeada por user_id, ver los pedidos de un usuario es una consulta a un solo shard. Un reporte de ventas totales del día, en cambio, debe recorrer todos los shards y combinar los resultados.

Desafíos y cuándo no conviene

El sharding cambia complejidad de escalado por complejidad operativa, así que conviene agotar antes las alternativas más simples.

Desafío Qué pasa Cómo se mitiga
Consultas entre shards Los JOINs y agregaciones sobre varios shards son más lentos Elegir una shard key que cubra las consultas frecuentes
Transacciones distribuidas Garantizar consistencia entre nodos es difícil Diseñar para que cada transacción toque un solo shard
Rebalanceo Agregar o quitar shards implica mover datos Consistent hashing, shards lógicos o una tabla de directorio
Regla práctica: antes de sharding, probar índices adecuados, particionamiento, réplicas de lectura y caché. Si luego de esto las escrituras o el volumen de datos siguen superando a un servidor, el sharding pasa a ser una opción razonable.

Sharding con CQRS

CQRS se combina con sharding sin problema: cada lado, escritura y lectura, se shardea por su cuenta, y lo único nuevo es cómo se sincronizan.

Comandos
→
Cluster escritura
→
Eventos / outbox
→
Cluster lectura

Los comandos entran por el router de escrituras. Un pipeline de eventos alimenta el cluster de lectura, que puede repartir los datos con otra clave. Si el objetivo es solo descargar lecturas del cluster principal, las réplicas de cada shard suelen alcanzar.

Conclusión

El sharding no es una “solución mágica”: es una decisión de arquitectura para casos muy concretos. Conviene cuando el crecimiento de datos y de carga ya excede un único nodo y se cuenta con una shard key natural. Cuando se diseña bien, permite mantener una base grande y exigente sin perder rendimiento ni aislar clientes.
